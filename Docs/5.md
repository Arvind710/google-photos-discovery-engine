## 5. The second coding defect: quiet successes coded Stage 2/5 (EC-CODE-18b)

### 5.1 How it was found
Reading the Stage 5 candidate's quotes while building the facts pack: "I literally just searched for 'cat on a countertop' and it found…", "searched 'forest' … first result. 12/10", coded Stage 5 with `why` "No failure occurred". Under `code_v1.1` a search that simply worked was coded the stage that worked (5 "search matched", 2 "lacked the date but found it"). D-9's v1.2 rule ("no failure is Stage 9") had only been applied to the Stage 0 suspects.

### 5.2 Fix
- `pipeline/classify/blocks.py`: `FAILURE_EVIDENCE` and `success_without_failure(stage, codes, outcome)` — Stage 2, 4 or 5, outcome `found` (not after a struggle), and no failure value in 5.1 (except parsed_ok), 5.2, 5.3 (except soft_ok), 5.4, 5.6 or 4.3. `success_suspects(con)`, `recode_suspects(con)` = stage0 ∪ success; `recode --yes` uses it.
- 13 flagged (9 core, 4 adjacent; a 5th adjacent story stated `5.1 code_mixed_language_failed` and was correctly not flagged). Re-coded with v1.2 through Batch: run `code-recode-20260926-144116-5cb9d9`, projected $0.197, actual **$0.178**, 13/13 coded (15 secondary quotes unverified, dropped). **12 moved to Stage 9**; one (Apple Photos search failed before Google Photos found it) stayed Stage 5 as `found_after_struggle`. 0 suspects remain.

  - `HARD_OUT_OF_SCOPE` (question text): success/failure/retrieval/abandonment rate, revenue, users counts ("people/users use"), market share … → NONE.
  - Planner disowned + no facts → NONE; methodological/`subject: method` → FULL from flags.
  - `needs` from the closed `REQUIREMENT_KINDS`; `subject: corpus` → needs = composition (totals always retrieved).
  - `_satisfied`: verbatim needs ≥ 2 stories; detail met by rows or ≥ 2 stories; reliability by channel 4; floor: if every counted row's `of` < 30 → answerable-with-gap ("!" → counts only, PARTIAL); a photo type **the question names** with < 30 stories → PARTIAL; a named type with no stories → PARTIAL.

  - `MISSING_CUTS` (question text): demographics, location/India/country, before/after or trends, Android vs iOS/platform, other apps' search quality → PARTIAL with the reason.

## 10. Gotchas learned this session

1. **Read the stories behind every headline cell.** The Stage 5 count was inflated by quiet successes; it was found only by reading the quotes the recommendation would cite.
2. **A re-code changes reliability.** If a re-coded story is in the dual sample, refresh the primary side (`agreement refresh`) — and expect agreement to fall if the second coder made the same mistake.
3. **"Checks passed" is not "correct".** The first recommendation passed and still misnamed the runner-up and misstated the metric step; sweep 4's answers passed number checks while pinning real numbers to the wrong rows. Read the output.
4. **Numbers must be checked against what the paragraph CITES**, not the whole brief — a real number on the wrong row is a misattribution the reader follows.
5. **Engine text is not testimony.** Only stories (and the asker's own words) may be quoted.
6. **Planner output varies between runs.** Decisions that change the route belong in code on the question's own words (SUBJECT_RULES, CLASS_WORDS, MISSING_CUTS, HARD_OUT_OF_SCOPE) — and must be tested on held-out paraphrases.
7. **Set timeouts on every model call.** The SDK default is 600 s; one stuck call held a sweep for 10 minutes. Under parallel load gpt-5 responses took ~100 s.
8. **A sweep run in the foreground loads modules at start** — edits made while it runs are not in its results.
9. **The CDP call limit is 45 s** — split "wait 35 s then resize" into two JS calls.
10. **Foreground `sleep` is blocked**; use `until …; do sleep …; done` or `run_in_background`.
11. **Streamlit skeletons:** the first screenshot shows grey placeholders; read the DOM.
12. **A patch script that stops halfway leaves modules inconsistent** (analyst passed `question=` to a verifier that did not accept it yet). Re-grep after a failed multi-file patch.
