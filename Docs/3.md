## 5. Phase 2 — segmentation

### 5.1 The prompt versus the fixtures, before any run

`prompts/segment_v1.md` (drafted in P1) disagreed with the fixtures in five places. All were fixed before the first run:
1. **seg-07 / seg-20 (follow-up posts):** "include a same-author follow-up if contiguous" contradicted "a story comes from ONE post". Now a later post by the same author is part of that story: it counts toward `reaches_stage` and its outcome goes in `reason`, but the span stays in the first post.
2. **seg-16 (a story told about someone else):** "the post of the person whose attempt it is" would attribute it to the wife. Now the story's author is the post's author.
3. **seg-11 / bb-07:** a quiet success IS a story.
4. **seg-19:** a question to others and a general habit are NOT stories.
5. **bb-05 / bb-11 / bb-13:** an irrelevant record yields no story, and the bucket scorer reads "no story" as `irrelevant`.

**Output design changed to anchors (D-7).** The model returns `post`, `start` (the first 5–12 words) and `end` (the last 5–12 words), copied exactly.
- `locate()` finds them with a regex inside that post only. The only tolerances are whitespace runs and straight vs curly quotes.
- The span is `text_clean[start:end]`, **verbatim by construction (T-1)**, at a fraction of the output tokens of a copied quote.

### 5.2 `pipeline/segment/stories.py`

- **Units and packing:**
  - A record is split into parts of at most `CHUNK_CHARS` = 10,000 on **post boundaries**. A single longer post is sent whole, never cut (EC-COL-4, A.5).
  - Units are packed into requests of at most `PACK_CHARS` = 10,000 characters and at most `PACK_RECORDS` = 12 records, with local ids R1…Rn. Post numbers are global.
  - `context` = `thread_context` (a title), sanitised, as an attribute. It is never a span source.
- **Output schema** (strict): `{"records":[{"id","stories":[{"post","start","end","bucket","reason","confidence","reaches_stage"}]}]}`.
- **`merge()`:**
  - locates each story and drops and COUNTS unfound (`unlocated`) and `overlapping` ones;
  - counts `missing_parts` (a unit the model gave no answer for);
  - clamps confidence to 0–1 and reaches_stage to 0–10;
  - asserts every stored text equals its slice.
- **`write_results()`:**
  - `stories` rows with `story_id = "<record_id>:<ordinal>"` and `author_key` from `posts_json`, the post the span sits in;
  - for a record with no located story: exclusion `no_story` (none returned) or `span_unverified` (returned but none located), at stage `segment`.
- **Commands** (`python -m pipeline.segment.stories …`):
  - `fixtures [--effort]`: sync run over all 74 fixture records (20 seg + 14 bucket + 40 authored), shuffled and packed as in the corpus; scored by `score_fixtures`; artifact `data/artifacts/segment_fixtures_<run>.json` (records `effort`).
  - `estimate`: projection using measured output tokens per record from the latest fixture artifact **at the same effort**. That rule is a fix: the first submit took its projection from a `minimal` run and recorded $0.82 instead of $1.64. The run is annotated with `estimate_correction`.
  - `submit`: the full corpus to the Batch API (`/v1/responses`, 24 h). It refuses if stories exist, or if the projection would cross 1.5 × $1.20 (the §8 estimate stays recorded, so T-19 still halts at $1.80).
  - `resubmit`: re-segment records that already have stories (`replace`).
  - `submit-new`: records added by a top-up that Pass 1 has not read (stage `segment-topup`).
  - `collect`: polls, and exits with code 3 if the batch isn't finished. Saves `data/batch/<run>_output.jsonl`, computes batch cost, applies the T-19 halt (`--accept-overrun` to write anyway), refuses to write if any request failed or is missing, and replaces rows when the manifest says `replace`. Manifests live in `data/batch/` (gitignored).
  - `retry`: re-code ONCE the records that had a skipped part or an unlocated story, synchronously, replacing their rows. It picks the latest ok run of `segment`, `segment-resegment` or `segment-topup`.
  - `dual [--n 60] [--with-stories]`: see §5.4.
- **Reasoning effort:** `low`. `minimal` was measured as 3× cheaper but failed story counts (75%) and T-9 (85.7%).

### 5.3 Remediation iterations on `segment_v1.md` (three, the cap)

1. **What "precise" means** (bucket fixtures were at T-9 85.7%; the model called typed keywords "precise"). Precise is about what the person REMEMBERS: a cue they were right to be sure of (a named person, the exact date or place, "yesterday", "the same day as a photo I already found"). A wrong or hedged cue is vague. Also: a known item wanted before any search is a story, and a new habit afterwards reaches 10.
   → T-9 100%, story counts 95%.
2. **`reaches_stage` is how far a story is TOLD, not where it first went wrong** (seg-12, a Stage-0 story, was scored 0). A changed query is "trying something else" (≥ 7). A hedged cue is fuzzy. One specific photo inside a person or category search is core when the rest is fuzzy; a person search failing outright is adjacent.
   → Story counts 95%, T-9 92.9%, `reaches_stage` at or above the fixture floor 94%, authored buckets 90%, all anchors located. **The corpus batch was submitted at this point.**
3. **A story needs a TARGET in the person's own library.** Added after the dual check (§5.4): general loss, recovery, backup, sync, storage, account, migration, Takeout and metadata problems, and photos on the web, are NOT stories unless a particular photo is sought.
   → Fixtures: counts 95%, T-9 100%. Used for the re-segmentation.

Known persistent fixture misses: **seg-17** (a feature request that mentions a mostly-red photo; never found as a story), and **bb-12** (flips between runs).

### 5.5 The gpt-5 confirmation step (D-8), `pipeline/segment/confirm.py`

- **Why:** gpt-5-mini over-finds stories in one direction; gpt-5 is the precision judge. gpt-5-mini stays the recall-first finder over every record, and gpt-5 runs over its candidates only.
- **Prompt:**
  - `prompts/confirm_v1.md` is a judging header, followed by the **definitions sections of `segment_v1.md`, verbatim** (from "## What a retrieval story is" to "## Output"), so the finder and the confirmer cannot drift apart.
  - Iteration 1 of the header added "strict does not mean narrow". gpt-5 had rejected [CTX]'s own "searching my wife's name shows nothing", plus short, vague wanted-photo stories. Now a set defined by a precise cue is a target (adjacent), and a vaguely described wanted photo in any language is a story.
- **Input per candidate:**
  - `source` and `context`;
  - the story text;
  - up to 1,500 characters of **later posts by the same author** in that record (these count toward `reaches_stage`).
- **Packing:** at most 15 candidates or 12,000 characters per request.
- **Output:** `{id, is_story, bucket, reaches_stage, reason}`.
- **Applying verdicts:**
  - `is_story` false → exclusion `no_story` at stage `segment` **with its `story_id`**. The row and its text stay (A.1).
  - Otherwise gpt-5's bucket is kept (the reason is replaced only when the bucket changed), and `reaches_stage` = **max**(finder, confirmer).
  - A record whose every story was rejected also gets a record-level `no_story` ("every story rejected by gpt-5 confirmation").
- **Commands:** `python -m pipeline.segment.confirm fixtures | submit | collect`.
  - `fixtures` runs find + confirm end to end on the fixtures and writes an artifact with `pipeline: "find+confirm"`.
  - `candidates()` skips story_ids already judged in any `data/artifacts/segment_confirm_*.json`, so a top-up confirms only its own new stories.
- **Fixture result, find + confirm:** story counts 90% (P2-MET-3 ≥ 85%), T-9 92.9% (≥ 90%), authored buckets 95%, all anchors located. Runs `confirm-fixtures-…092801-0136b4` (before the header fix: T-9 85.7%) and `…092950-981293` (after).

### 5.8 Why the core is thin (the finding)

## 11. Gotchas learned this session

1. **Apify bills after SUCCEEDED.** Read cost only once it settles (`settled_usage`). Guard spend with the **account** total (`GET /v2/users/me/limits`), not per-run figures.
2. **gpt-5-mini over-finds retrieval stories** in public text: it treats "lost/deleted/recover" complaints as stories even when told not to. gpt-5 follows the definition. Never trust mini's story counts alone.
3. **Estimate by effort.** Reasoning tokens make `low` about 3× `minimal` on output. A projection from the wrong effort's fixture run halved the estimate once.
4. **A dual-model sample must hold stories.** Three in four records hold none, so a mixed sample left T-6 with 8 matched stories.
5. **Batch timing:** 832 requests took about 30 minutes (some minutes of `validating`); 110 to 448 requests took 5 to 15 minutes. `collect` exits with code 3 until the batch is done; poll it in a background loop.
6. **The YouTube search term → recovery-tutorial trap:** Hinglish lexicon terms ("photo nahi mil rahi", "purani photo kaise dhoondhe") surface deleted-photo recovery tutorials with thousands of comments, and yield almost no core stories.
7. **The GP Help listing at `max_results=10000` returns nothing.** 5,000 works.
8. **The Stack Exchange keyless quota is 300 a day.** It was nearly spent (15 left) after `-n 75`.
9. **`evals/report.py` overwrites the day's gate file.** Hand-written appendices must be re-appended after every regeneration.
10. **`!` commands inside a longer message are not executed.** They must start their own prompt line.
11. **The auto-mode classifier blocked `gh run watch`/`gh run list`** ("Out-of-Place Publication"). Pushes to this repo were allowed. Rebasing this session's own unpushed commit onto the PM's remote commit was fine after inspecting it.
